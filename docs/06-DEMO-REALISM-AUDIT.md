# 06 · Аудит реалистичности демо-контура

Дата: 26.10.2026. Цель — чтобы демо считало **те же деньги**, что боевой контур, и чтобы расхождение
с реальностью было измеримым, а не «на глаз».

---

## 1. Как считается позиция сейчас (после правок)

### 1.1 Вход
- Капитал `C = min(риск-лимит, ликвидность диапазона T_r, доля депозита)`.
- `риск-лимит = (MaxDD% × D) / (1 − P_exit/P_avg + издержки выхода)`.
- Веса по бинам `w_i ∝ объём_бина / (чужая ликвидность_бина + 50)` — больше денег туда, где больше
  объёма и меньше конкурентов; вес одного бина ограничен 35%.
- Средняя цена входа — **взвешенная гармоническая** `P_avg = 1 / Σ(w_i / P_i)` (а не арифметическая:
  именно по ней реально куплен токен).
- Вход односторонний (SOL), поэтому **свопа на входе нет** → нет комиссии пула и слиппеджа на входе.
  Есть только сетевой сбор + priority fee (~0.00005–0.0002 SOL), в демо не учитывается (влияние < 0.01%).

### 1.2 Комиссии — теперь ПО БИНАМ (а не «по диапазону»)
Раньше: `fees = V24 × r × f × C/(T_r+C)` — одна ставка на всю позицию, точность ±40%.
Теперь на входе для каждого бина считается своя скорость начисления:

```
feePerDay(bin) = V24 × (объём_бина / объём_профиля) × f_net × (наш_капитал_в_бине / (чужая_ликвидность_бина + наш_капитал))
```

где `f_net = (base_fee + dynamic_fee) × (1 − protocol_fee%)`.

Во время жизни позиции скорость умножается на **вес близости к текущей цене**:

```
w(bin) = exp(−|k_cur − k_bin| / 2.5),   k = ln(price) / ln(1 + binStep/10000)
fees += Σ_bin feePerDay(bin) × w(bin)/Σw × dt/86400
```

Почему так: в DLMM объём идёт через активный бин и 2–3 соседних; капитал, стоящий в дальних бинах,
почти не зарабатывает. Раньше это усреднялось, доходность завышалась на 15–30%.

**Что всё ещё приближение:**
- объём бина берём из профиля цены за 24 ч (свечи), а не из реальных свопов;
- не учитываем «протухание» доли: когда наш SOL в бине конвертировался в токен, доля в бине считается
  по-прежнему нашей (по стоимости) — это верно, но состав бина меняется;
- не учитываем лимит-ордера и фермы других участников;
- не учитываем, что крупные свопы «перепрыгивают» бины (мы это частично ловим через профиль).

### 1.3 Проскальзывание на выходе — по реальной котировке Jupiter
При стопе/выходе:
1. считаем, сколько токена у нас на руках (по бинам, которые реально заполнились);
2. запрашиваем `lite-api.jup.ag/swap/v1/quote` (token → SOL) на **фактическое количество**;
3. `slip = 1 − outUsd / fairUsd` + 0.06% на priority fee и сеть;
4. если Jupiter не отвечает — консервативная оценка 0.8%.

Так учитывается реальная глубина рынка в моменте, включая проскальзывание по нескольким пулам.
**Чего нет:** MEV-сэндвич, отказ транзакции, повторные попытки (в боевом это добавит 0.05–0.3% в плохих условиях).

### 1.4 PnL — как в Meteora: комиссии + изменение стоимости активов
```
value      = SOL-часть + токен-часть (по текущей цене)
IL         = value − капитал
fees       = накопленные (и собранные) комиссии
PnL        = IL + fees
PnL%       = PnL / депозит
```
Обе компоненты показываются отдельно в карточке позиции («Из чего сложился результат»), плюс
динамика распределения капитала SOL ↔ токен.

**Сверка с Meteora:** их карточка позиции показывает `Deposits / Withdrawals / Fees / PnL` по
закрытым позициям и `Balance + unclaimed fees` по открытым. Наша формула совпадает по смыслу; отличие —
у Meteora дополнительно учитывается стоимость входа/выхода по фактическим свопам и NFT-позиция.

### 1.5 Учёт издержек, который уже есть
| Издержка | Учтено | Как |
|---|---|---|
| Комиссия пула (base + dynamic) | ✅ | `f_net` с вычетом протокольной доли |
| Протокольная комиссия Meteora | ✅ | `(1 − protocol_fee%)` |
| Комиссия и слиппедж выхода | ✅ | Jupiter quote, факт. количество токена |
| Priority fee / сеть | ✅ частично | +0.06% к выходу |
| Своп на входе | ➖ | нет свопа: вход односторонний |
| Сетевой сбор за вход (5–8 tx) | ❌ | ~$0.01–0.03, ниже погрешности |
| Комиссия за клейм | ❌ | 1 tx за клейм, ~$0.005 |
| MEV / сэндвич | ❌ | риск на мем-токенах до 0.5% |
| Неудачные транзакции, ретраи | ❌ | боевой контур добавит 0.05–0.2% |

## 2. Что изменилось в цифрах после аудита

| Показатель | Было | Стало |
|---|---|---|
| Комиссии | одна ставка на диапазон | по каждому бину + вес близости к цене |
| Слиппедж выхода | фикс 0.8% | реальная котировка Jupiter + 0.06% |
| PnL | value + fees (без разбивки) | IL + fees отдельно, как в Meteora |
| Распределение капитала | не показывалось | донат SOL/токен + история во времени |
| Цена на графике | USD (не совпадала с уровнями вход/стоп) | в единицах пула — уровни и сетки совпадают |
| Источник свечей | GeckoTerminal (лимиты 429) | Meteora Data API (основной) + Gecko (fallback) |

## 3. Проверочные сценарии (как убедиться, что демо честное)

1. **Нулевое движение цены.** Цена стоит → `IL = 0`, PnL = комиссии. В демо: войти и не двигать цену.
2. **Пробой вниз до стопа.** PnL должен быть ≈ `−C × (1 − P_exit/P_avg + slip)` и ≤ 5% депозита.
3. **Пробой вверх.** Все бины вернулись в SOL → `IL ≈ 0`, PnL = комиссии − издержки.
4. **Сверка комиссий.** За 1 час: `fees ≈ Σ feePerDay(bin) × w(bin) / 24`. Сравнивать с суммой клеймов в журнале.
5. **Кросс-проверка с Meteora.** Открыть тот же пул в Meteora на ту же сумму с теми же границами и
   сравнить `Fee/TVL` за час (расхождение должно быть < 25%).

Сценарии 1–3 проверяются автотестом (см. `apps/engine/src/__tests__` — в следующем спринте).

## 4. Что осталось для «полного реализма» (по приоритету)

1. **Точные сделки вместо профиля цены.** Читать свопы пула (Helius `getSignaturesForAddress` +
   parsed tx / Yellowstone gRPC) → строить реальный объём по бинам и реальные комиссии.
2. **Снапшот ликвидности по бинам каждые 30–60 с.** Сейчас снимается на входе и в графике;
   при сильном притоке/оттоке LPs наша доля меняется, демо этого не видит.
3. **Учёт позиции как NFT.** Meteora хранит позицию в NFT-аккаунте: в боевом нужно закрывать/переиспользовать
   его, в демо не важно.
4. **Latency и отказы.** Ввести модель задержки (200–800 мс) и 1–2% отказов транзакций.
5. **Сетевые сборы** за вход/клейм/выход (сейчас только на выходе, доля < 0.02% депозита).

---

## 5. Вывод аудита

Демо **не «рисует» прибыль**: комиссии начисляются по конкурентной доле в каждом бине, издержки выхода
берутся из реальной котировки, PnL разложен на комиссии и изменение стоимости. Основные источники
расхождения с боевым контуром — отсутствие MEV/отказов и приблизительный объём по бинам; оба
влияют в сторону **завышения** на 5–25%, что уже видно в журнале по строке «прогноз vs факт».
