## 1.2 Что уже сделано правильно (не ломать)

- **Сетевая изоляция корректна.** Caddy проксирует только `127.0.0.1:$WEB_PORT`; движок на `127.0.0.1:8787` извне недоступен. Наружу открыты только 80/443.
- **Прокси к движку требует сессию.** `app/api/engine/[...path]/route.ts` перепроверяет `readSession()` на GET **и** POST — это defence-in-depth даже при байпасе middleware.
- **Cookie:** `httpOnly`, `sameSite=lax`, `secure` в production. `sameSite=lax` закрывает CSRF на POST из чужих сайтов.
- **`.env` не в git** (`.gitignore`), в репозитории только `.env.example`.
- **`install.sh` не стирает боевые данные** при деплое (rsync-исключения для `.env` и `data/*.db`) — это исправление критичного бага, регрессию не допускать.
- **Парольная авторизация обязательна**: без `ADMIN_PASSWORD` роут отдаёт 500, а не пускает.
- **Журнал и API отдают данные только за сессией**; `Cache-Control: no-store` на прокси.

## 1.3 Приоритетный план исправлений

**Сейчас (30 минут, до любого публичного доступа):**

1. Обновить Next.js: `cd apps/web && npm i next@14.2.35` (в пределах 14.x, без ломки API) → пересобрать. Закрывает CVE-2025-29927 и большинство advisories из блока `next`.
2. Добавить в `login/route.ts` простой in-memory лимит: 5 попыток / 10 минут на IP + задержка 300 мс на неудачу + запись в журнал движка (`journal("WARN", "неудачный вход с IP …")`).
3. Убрать `.env` и `data/*.db` из `bundle.sh` (`--exclude ".env" --exclude "data/*.db*"`), а секреты на сервер доставлять отдельно.
4. Убрать дефолт секрета: если `AUTH_SECRET` не задан — **падать при старте**, а не подписывать публичным ключом.

**В течение дня:**

5. `applySettings()` — белый список ключей + клампы (`maxPositions ≤ 3`, проценты 0…100, суммы > 0). Отклонять неизвестные ключи.
6. Заголовки безопасности: CSP (`default-src 'self'`), `X-Frame-Options: DENY`, `Permissions-Policy`, в Caddy-блок.
7. Валидация `mint` (base58, 32–44 символа) в `/api/icon`, валидация `date` в `/api/journal/download`.
8. systemd-hardening для обоих юнитов + `Environment=HOME=/opt/meteora-terminal`.
9. Бэкап SQLite по cron (`sqlite3 data/engine.db ".backup …"`, ротация 14 дней) — по образцу ESMAR.

**Перед live (см. часть 2):**

10. Локальный API движка — с токеном (`Authorization: Bearer`, генерируется в `.env`) или на unix-сокете вместо TCP.
11. Ротация `AUTH_SECRET`/`ADMIN_PASSWORD` на длинные случайные (`openssl rand -base64 32`), лог успешных/неудачных входов.
12. `npm audit fix` для некритичных цепочек; `toml`/`uuid` без фикса — принять риск (используются только внутри Solana SDK при разборе доверенных данных).

# ЧАСТЬ 2. Аудит готовности боевого режима

## 2.1 Доказательства: live-режима нет

Проверено grep-ом по всему `apps/engine/src`:

```
addLiquidity | removeLiquidity | claimFee | createPosition | initializePosition
sendTransaction | signTransaction | sendRawTransaction | Keypair | Wallet(
```
→ **0 совпадений.**

Что реально умеет работать с цепочкой — единственный файл `chain.ts` (79 строк), и он **только читает**:
`Connection`, `DLMM.create`, `getActiveBin`, `getBinsBetweenLowerAndUpperBound`. `swaps.ts` (711 строк) — тоже чтение:
`getSignaturesForAddress`, `getTransaction`, разбор логов свопов для аналитики кошельков.

Что происходит «на самом деле»:

| Слой | Как реализовано | Что это значит в live |
|---|---|---|
| Вход в позицию | `positionValue()` / математика бинов, `db.insert positions` | Позиция в БД, **в пуле её нет** |
| Начисление комиссий | `accrueFees()` — модель по объёму пула и весам бинов | Виртуальные деньги |
| CLAIM | `pos.feesClaimed += claimed`, `this.cash += claimed` | В цепочке ничего не снято |
| Выход/ребаланс | `closePositionById()` — пересчёт PnL и запись события | Ликвидность осталась бы в пуле |
| `BOT_MODE` | `env.mode` → подпись `mode=live` в журнале и DTO | **Не влияет ни на одну ветку логики** |
| Ключи | `TRADING_WALLET_SECRET_BASE58`, `TRADING_WALLET_PUBKEY`, `WALLET_ENCRYPTION_KEY` есть в `.env` как **пустые строки** и **не упоминаются ни в одном файле кода** | Подписывать нечем и негде |

Вывод: **`BOT_MODE=live` — косметический флаг.** Включение ничего не включает. Ни один доллар/лот не может быть
потерян по технической ошибке — но и заработать нечего.

## 2.2 Чего не хватает до live — по блокам

### A. Исполнение (главный отсутствующий модуль)

Нужен новый слой `apps/engine/src/executor.ts`:

1. **Кошелёк и подпись.** `Keypair.fromSecretKey(bs58.decode(secret))`, подключение к RPC с `commitment: "confirmed"`.
   Ключ — только в памяти процесса, читается из `.env` (или расшифровывается AES-256-GCM через `WALLET_ENCRYPTION_KEY`), никогда не логируется.
2. **Открытие позиции.** `dlmm.initializePositionAndAddLiquidityByStrategy({ positionPubKey, user, totalXAmount, totalYAmount, strategy: { minBinId, maxBinId, strategyType } })` —
   распределение по бинам уже посчитано в `math.ts`, его надо передать в SDK, а не «нарисовать» в БД.
3. **Снятие/клейм.** `removeLiquidity`, `closePosition`, `claimSwapFee` из `@meteora-ag/dlmm`.
4. **Свопы.** Ребаланс и ротация требуют обмена токена; нужен Jupiter-своп с **проверкой слиппеджа** и `maxAccounts`, а не только quote (сейчас quote используется для оценки издержек).
5. **Приоритетные комиссии и лимиты газа.** `ComputeBudgetProgram.setComputeUnitPrice` + ретраи с эскалацией; иначе в моменты волатильности транзакции не долетают — а именно в эти моменты бот и должен действовать.

### B. Надёжность и безопасность денег

6. **Идемпотентность.** Каждое действие — запись в `position_events` со статусом `pending → sent → confirmed/failed` и `signature`.
   При рестарте процесс **сверяет БД с цепочкой** (`getPositionsByUserAndLbPair`), а не с собственной памятью.
   Сейчас есть `reconcileCash()` только для виртуального кэша.
7. **Kill-switch.** Кнопка «СТОП» (одна), которая: останавливает цикл, отменяет незавершённые действия, **не закрывает позиции аварийно**, шлёт уведомление в TG.
   Сейчас `engine.halted` есть, но он не связан ни с какими внешними рисками и не останавливает уже начатую транзакцию.
8. **Жёсткие лимиты на уровне исполнителя** (не только стратегии): максимум капитала на позицию, максимум позиций = 3, дневной стоп-лосс, максимум транзакций в час, «не торговать, если баланс кошелька ниже X».
   Сейчас `applySettings` позволяет выставить что угодно (S-07) — в live это прямой путь к сливу.
9. **Обработка ошибок цепочки:** `blockhash not found`, `slippage tolerance exceeded`, `insufficient lamports`, `transaction expired`, отказ RPC, реорг.
   Нужна классификация: «повторить», «отменить», «остановиться и позвать человека».
10. **Резервный RPC и health-check.** `SOLANA_RPC_FALLBACK_URL` в `.env` есть, но код его не использует — переключение отсутствует.

### C. Наблюдаемость

11. **Алерты в Telegram** (`TG_BOT_TOKEN`, `TG_CHAT_ID` есть в `.env`, но не используются): позиция открыта/закрыта, ошибка транзакции, дневной стоп, RPC недоступен, капитал ниже порога.
12. **Сверка капитала с цепочкой раз в N минут**: сумма `lamports` + токенов на кошельке против `equity` в БД. Расхождение > 1% → стоп и алерт.
13. **Журнал** уже пригоден для ИИ-разбора; в live нужно добавить `signature`, `slot`, `fee` в JSON-контекст каждой операции.

### D. Процесс запуска (обязательный)

14. **Devnet-прогон** ≥ 48 часов на реальных пулах Meteora devnet: полный цикл вход → комиссии → ребаланс → выход, с проверкой каждого шага в explorer.
15. **Малые деньги на mainnet**: 0.3–0.5 SOL trading capital + отдельный газовый запас. Не более 1 позиции, `POSITION_BUDGET_PCT` ≤ 20.
16. **Правила остановки:** после 3 убыточных сделок подряд, при дневной просадке 5%, при расхождении баланса > 1% — останов и ручной разбор.
17. **Юридический момент:** бот торгует вашими же средствами (не привлекает чужие) — риск регуляторный минимален, но налоги на PnL и на свопы нужно считать отдельно. Это не блокер запуска, но зафиксировать.

## 2.3 Оценка объёма работ

| Блок | Оценка |
|---|---|
| `executor.ts` (вход/выход/клейм/своп + подпись) | 3–4 дня |
| Идемпотентность + сверка с цепочкой | 2 дня |
| Лимиты, kill-switch, классификация ошибок, резервный RPC | 2 дня |

| Devnet-прогон + отладка | 2–3 дня |
| **Итого до «можно включать live»** | **~10–12 рабочих дней** |

Плюс параллельно — 1 день на пункты 1–12 из раздела 1.3.

## 2.4 Чек-лист «готов к live» (все пункты обязательны)

- [ ] S-01…S-07 закрыты (безопасность)

## 3.2 Боевой режим — реализовано

Новый слой `apps/engine/src/executor.ts` (≈500 строк) + `alerts.ts`:

- **Реальные операции DLMM**: `initializePositionAndAddLiquidityByStrategy`, `removeLiquidity(…, shouldClaimAndClose: true)`, `claimSwapFee`.
- **Подпись**: base58 / JSON / `enc:` (AES-256-GCM через `WALLET_ENCRYPTION_KEY`); сверка ключа с `TRADING_WALLET_PUBKEY`; утилита `scripts/encrypt-wallet.ts`.
- **Три условия включения** (`armed()`): `BOT_MODE=live` + `LIVE_EXECUTION=true` + валидный ключ. Иначе — прежняя симуляция без изменений.
- **Лимиты в исполнителе**: ≤ 3 позиций, `LIVE_MAX_POSITION_USD` (урезает сумму), слиппедж, приоритетная комиссия, неприкосновенный резерв SOL.
- **Идемпотентность**: таблица `onchain_ops` (pending → confirmed/failed, `signature`, `position_pubkey`), проверка незавершённых операций.
- **Инвариант «сначала цепочка, потом база»**: при ошибке открытия — откат записи и `HALT`; при ошибке закрытия — запись не создаётся, `HALT` + алерт.
- **Сверка с цепочкой** каждые `LIVE_RECONCILE_MINUTES`: «есть в базе, нет в пуле» → остановка и алерт; резерв SOL ниже нормы → алерт.
- **Резервный RPC**: при ошибке основного — `SOLANA_RPC_FALLBACK_URL`.
- **Алерты в Telegram** (`TG_BOT_TOKEN`, `TG_CHAT_ID`), троттлинг 5 мин; критические — мгновенно.
- **API**: `/api/live/status`, `/api/live/reconcile`; в UI — карточка «Боевой режим» в Кабинете (armed, лимиты, причины блокировки, последние операции, кнопка сверки).

Документация запуска: `docs/12-LIVE-MODE.md`. Переменные: `LIVE_*` в `.env.example`.
