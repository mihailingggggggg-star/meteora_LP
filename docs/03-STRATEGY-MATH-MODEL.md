# 03 · Стратегия и математическая модель входа

Цель: **≥ +2% к депозиту в сутки только за счёт комиссий**, 15–18 часов в сделке из 24,
жёсткий предел убытка **−5% от депозита** при пробитии всех сеток.

Ниже — модель, которую реализует движок. Все числа считаются на реальных данных API (объём, TVL, ликвидность по бинам, ставка комиссии).

---

## 1. Постановка позиции (что именно мы открываем)

Пара всегда `ТОКЕН / SOL`. Входим **одной стороной — SOL (quote)** в бины около текущей цены:

```
цена
 ▲
 │        ┌── bin сверху: сюда кладём чуть-чуть (продажа токена при отскоке)
 │  P0 ───┤ активный бин
 │        │  ЗОНА 1 (узкая, рабочая): ближайший узел объёма СНИЗУ
 │  ....  │  40–50% капитала, BidAsk
 │        │
 │        │  ЗОНА 2 (широкая, усреднение): следующий узел объёма ниже,
 │  ....  │  выходим немного за его нижнюю границу. 50–60% капитала
 │  ▓▓▓▓  ▼
 │  P_exit = нижняя граница зоны 2 − 1 бин  → СТОП: продаём токен в SOL
 └──────────────────────────────────────────► время
```

Почему BidAsk: в DLMM распределение `BidAsk` — **инверсная кривая, больше ликвидности у краёв**, официально рекомендуется для «DCA-входа в токен одной стороной». Ровно наш случай: пока цена падает, SOL конвертируется в токен по всё более низким ценам (усреднение вниз); когда цена возвращается — токен конвертируется обратно в SOL дороже + комиссии.

Почему две зоны: зона 1 собирает комиссии в рабочем диапазоне (там проходит объём), зона 2 — усредняет позицию и ловит отскок от следующего узла. Это и есть «бид-аск распределение капитала для лучшей средней точки входа».

## 2. Средняя цена входа (точная формула)

Капитал распределён по бинам весами `w_i` (сумма = 1). В бине `i` мы получаем токенов `q_i / P_i`, где `q_i = w_i · C`.
Средняя цена покупки — **взвешенная гармоническая**:

```
P_avg = C / Σ(q_i / P_i) = 1 / Σ(w_i / P_i)
```

Это корректная математическая средняя: не арифметическая (она завышает), а именно та, по которой реально куплен токен.

## 3. Прогноз комиссий (ядро модели)

Обозначения:
- `V24` — объём пула за 24 ч (API: `volume.24h`)
- `r` — доля объёма, которая проходит **внутри нашего диапазона** (считаем по сделкам/свечам: время-в-диапазоне × объём)
- `f` — эффективная ставка комиссии: `f = (base_fee + dynamic_fee) × (1 − protocol_fee/100)`
- `T_r` — USD-стоимость **чужой** ликвидности в наших бинах (читаем с цепи по бинам: `tokenX_amount·Px + tokenY_amount·Py`)
- `C` — наш капитал в этих же бинах
- `u` — коэффициент утилизации (0.5–0.9): не весь наш капитал постоянно «работает», часть стоит вне прохода цены

Комиссии в диапазоне за сутки: `F_r = V24 · r · f`
Наша доля: `s = C / (T_r + C)`
Наш доход: `E_day = F_r · s · u`

**Доходность на наш капитал:**

```
R_day = E_day / C = (V24 · r · f · u) / (T_r + C)
```

Три важных следствия (это не очевидно, но именно так работает DLMM):

1. **Доходность почти не зависит от нашего размера, пока `C << T_r`** — она равна интенсивности комиссий в диапазоне.
2. **Оversizing убивает доходность**: при `C >> T_r` вся формула вырождается в `V24·r·f/C` — мы едим свой же объём. Оптимум по доходности — `C ≈ T_r` (забираем ~50% комиссий диапазона).
3. **Проверка ваших фильтров**: при `V24/TVL = 25%/день` (TVL/Vol = 400%), `f = 1%`, `r = 0.5`, `u = 0.8` и зоне, в которой лежит 5% TVL:
   `R = 0.25 · 0.5 · 0.01 · 0.8 / 0.05 = 2.0%/день` ✅ — цель достижима, но **только на нижней границе вашего фильтра** (400–600%), где объём высокий. При 1300% (V/TVL = 7.7%/день) максимум ≈ 0.6%/день — такой пул цель не даёт.
   → Модель считает это для каждого кандидата и **отбраковывает** пулы, которые физически не могут дать 2%.

Поэтому в скринере появляется интегральная метрика вместо «на глаз»:

```
score = R_day(base case)  при 15-часовом горизонте:  R_15h = R_day · (15/24)
```

Плюс три сценария:
- **pessimistic**: `V24 × 0.5`, `r × 0.8` → проверяем, что убыток по комиссиям не создаёт ложной уверенности
- **base**: как посчитано
- **optimistic**: `V24 × 1.3`

## 4. Предел риска −5% от депозита (определяет размер позиции)

Стоп срабатывает на `P_exit`. К этому моменту весь наш SOL уже сконвертирован в токен по средней `P_avg`, и мы его продаём.

```
потери_на_цене   = 1 − P_exit / P_avg
издержки_выхода  = c  (своп-комиссия + слиппедж + priority fee; берём из реальной котировки Jupiter)
worstLoss        = C · (1 − P_exit/P_avg + c)
ОГРАНИЧЕНИЕ:       worstLoss ≤ 0.05 · D
```

Отсюда **максимальный капитал в сделке**:

```
C_max_risk = 0.05 · D / (1 − P_exit/P_avg + c)
```

Пример: депозит `D = 500`, глубина сеток = 6% (зона 2 низ), `P_avg` на 1.8% ниже входа → `1 − P_exit/P_avg ≈ 4.3%`, `c = 0.8%` → `C_max_risk = 25 / 5.1% = 490` → фактически весь депозит, но комфортнее 60–70%.

Если глубже сетки → допустимый капитал меньше. Это автоматически держит риск.

**Итоговый размер позиции:**

```
C = min(C_max_risk, C_yield_opt ≈ T_r, свободный_баланс)   и   C ≤ 0.7 · D (запас)
```

Проверяем оба условия; если при этом `R_15h < 2%` — пул не подходит, берём следующий по score.

## 5. Геометрия сеток из вертикального объёма

1. Строим **volume profile**: сделки/свечи за 24–72 ч → объём по ценовым уровням (в терминах бинов пула).
2. Ищем **узел объёма №1** в коридоре `−2% … −6%` от цены. Зона 1 = `[нижняя граница узла − 1 бин … верхняя граница узла]` (пересекаем с «не выше текущей цены»).
3. Ищем **узел объёма №2** ниже. Зона 2 = `[нижняя граница узла №2 − 1–2 бина … нижняя граница зоны 1]`. Выход чуть ниже узла — «из этой зоны цену должны вытолкнуть обратно».
4. Число бинов в зоне ограничиваем по `bin_step` (диапазон ≤ ~35 бинов на зону: меньше газа и понятнее управление).
5. Веса `w_i`: пропорционально `объём_бина / (T_r_бина + наш_капитал)` — больше денег туда, где больше объёма и меньше конкурентов. Затем нормируем и проверяем `P_avg` и `worstLoss`.

## 6. Жизненный цикл сделки (автомат)

```
СКАНИРОВАНИЕ (каждые 5 мин, 24/7)
  фильтры → кандидаты → модель по каждому → берём max(score) если R_15h ≥ 2% и риск ≤ 5%
  ↓
ВХОД: init position (зона 1 + зона 2), запись в журнал, WS-подписка на цену
  ↓
В РАБОТЕ (15–18 ч целевых)
  ├─ сбор комиссий по расписанию (например каждые 2 ч) → в SOL, чтобы не копить токен
  ├─ контроль: цена внутри диапазона? ликвидность/объём не развалились? TVL не упал вдвое?
  ├─ СТОП: цена ≤ P_exit  → мгновенная продажа токена (Jupiter, priority fee, 2 RPC, fallback своп в пуле)
  │        → решение: перезайти в этот пул или искать новый (сравниваем score текущего и лучших кандидатов)
  └─ ВЫХОД ВВЕРХ: цена > верх зоны 1
        → ждём 5 минут
        → если не вернулась в диапазон: закрыть обе сетки, продать остаток токена в SOL, переставить сетки выше
          (пересчёт геометрии от новой цены; если пул стал хуже — искать новый)
  ↓
ЗАКРЫТИЕ: фиксация PnL (комиссии + IL), запись в journal, обновление аналитики, скан заново
```

Правила выбора «перезайти vs новый пул»: сравниваем `score` текущего пула (пересчитанный на текущий момент) с лучшим кандидатом.
Перезаходим, только если `score_current ≥ 0.85 · score_best`, иначе — в новый. Это ровно то, что вы просили в ТЗ.

## 8. Что делать, если 2%/день недостижимо

Честный ответ: цель агрессивная. Поведение движка (настраиваемо):
- **строгий режим**: нет пула с `R_15h ≥ 2%` → стоим в SOL, ждём (деньги не работают, но и не теряют);
- **мягкий режим**: берём лучший пул, если `R_15h ≥ 1.2%`, и пишем в журнал, что цель дня не выполнена;
- **уведомление** в Telegram: «кандидатов с 2% нет, лучший 0.9% — жду».

В демо-контуре это видно сразу: за 24 ч накопится статистика «сколько раз цель достигалась» — по ней и подкрутим фильтры (это и есть работа с журналом).
