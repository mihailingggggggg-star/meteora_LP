# 12 · Боевой режим: как устроен и как включать

Дата: 27.10.2026. Код: `apps/engine/src/executor.ts`, `alerts.ts`, таблица `onchain_ops`.
По умолчанию боевой режим **выключен** и ничего не делает.

---

## 1. Три условия, без которых live не включится

```
BOT_MODE=live              # движок считает себя боевым
LIVE_EXECUTION=true        # разрешение на реальные транзакции
TRADING_WALLET_SECRET_BASE58=<ключ>   # ключ кошелька (base58, JSON или enc:…)
```
Плюс `TRADING_WALLET_PUBKEY` — адрес для сверки (если задан и не совпал с ключом, кошелёк не загрузится).

Проверить готовность в любой момент:

```bash
curl -s localhost:8787/api/live/status | jq '.armed, .checks, .limits'
```
или в интерфейсе: **Кабинет → Боевой режим** — там же список причин, почему live ещё не активен,
и кнопка «Сверить с цепочкой».

## 2. Кошелёк

Отдельный кошелёк, только под торговлю (не основной).

```bash
# 1) положить ключ, зашифровав его AES-256-GCM (рекомендуется)
export WALLET_ENCRYPTION_KEY="$(openssl rand -base64 32)"   # в .env
npx tsx scripts/encrypt-wallet.ts '<base58-или-JSON-ключ>'   # печатает enc:<iv>:<tag>:<data>

# 2) в .env
TRADING_WALLET_SECRET_BASE58=enc:....
TRADING_WALLET_PUBKEY=<публичный адрес>
```
`WALLET_ENCRYPTION_KEY` хранить отдельно от `.env` не нужно — но `.env` должен быть `chmod 600`
и не попадать в архивы (bundle.sh уже исключает).

Форматы ключа: base58-строка, JSON-массив (экспорт Phantom), `enc:…`.

## 3. Лимиты, зашитые в исполнитель

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `LIVE_MAX_POSITIONS` | 3 | больше 3 позиций не откроется, даже если в UI поставить иначе |
| `LIVE_MAX_POSITION_USD` | 100 | сумма позиции урезается до лимита, в журнал пишется WARN |
| `LIVE_SLIPPAGE_PCT` | 1.5 | допуск по цене при добавлении ликвидности |
| `LIVE_PRIORITY_FEE_MICROLAMPORTS` | 50 000 | приоритетная комиссия, чтобы транзакция долетела |
| `LIVE_MIN_SOL_RESERVE` | 0.03 | неприкосновенный запас SOL на газ и аренду позиции |
| `LIVE_RECONCILE_MINUTES` | 10 | период сверки базы с цепочкой |

Дополнительно исполнитель отказывается открывать позицию, если:
- SOL на кошельке меньше `резерв + половина капитала позиции`;
- сумма меньше одного бина по каждому токену;
- нет цены одного из токенов пула;
- уже есть незавершённая операция того же типа по этой позиции (идемпотентность).

## 4. Как идёт сделка

```
сканер → план (бины, диапазон, капитал)
      → INSERT positions (база, status=open)
      → executor.openPosition:
            onchain_ops(OPEN, pending)
            initializePositionAndAddLiquidityByStrategy  → подпись → подтверждение
            onchain_ops(confirmed, signature, positionPubkey)
      → tick: комиссии, диапазон, ротация
      → executor.claimFees (по времени/порогу)   → onchain_ops(CLAIM)
      → executor.closePosition:
            removeLiquidity(bps=10000, shouldClaimAndClose=true) → onchain_ops(CLOSE)
      → только после подтверждения — запись PnL в базу
```

Ключевая инвариантность: **сначала цепочка, потом база.** Если транзакция не прошла —
запись откатывается (открытие) или не создаётся (закрытие), торговля останавливается.

## 5. Что происходит при сбое

| Событие | Реакция |
|---|---|
| Не удалось открыть позицию | запись удаляется, кэш возвращается, `HALT`, критический алерт в TG |
| Не удалось закрыть позицию | позиция остаётся в базе как есть (не «рисуем» выход), `HALT`, алерт |
| Не удалось снять комиссии | комиссии остаются в `feesAccrued`, повтор на следующем тике, алерт |
| RPC не ответил | переключение на `SOLANA_RPC_FALLBACK_URL`, WARN в журнал |
| Сверка: позиция есть в базе, но нет в цепочке | `HALT` + алерт со списком позиций |
| Сверка: SOL ниже резерва / расхождение | `HALT` + алерт |
| Ручная кнопка «Пауза» | `engine.running=false`, новые сделки не открываются |

Все алерты — в Telegram (`TG_BOT_TOKEN`, `TG_CHAT_ID`), с троттлингом 5 минут
для повторяющихся и без троттлинга для критических.

## 5.1 Репетиция (dry-run) и докупка токена

- `LIVE_DRY_RUN=true` — движок собирает и **симулирует** транзакции (open/close/claim), пишет результат
  в журнал (`LIVE … симуляция ok (units N)`) и **не отправляет** их. Это бесплатная репетиция на mainnet:
  видно, что транзакция собралась и прошла бы, без риска деньгами.
- При открытии позиции 50/50 бот проверяет токеновую половину и, если её нет, **докупает через Jupiter**
  (`ensureToken`): считает нехватку, берёт котировку, отправляет swap, ждёт подтверждения.
  Раньше этого шага не было — первая же live-позиция падала бы на «insufficient funds».
- Кластер определяется по RPC: адрес с `devnet` → `DLMM.create(..., {cluster:"devnet"})`, иначе mainnet-beta.

## 5.2 Всё из интерфейса (без правки .env руками)

Кабинет → **Боевой режим**:

1. **«Подключить кошелёк»** — вставить приватный ключ (base58 или JSON-массив) и, по желанию, адрес для сверки.
   Ключ проверяется (адрес должен совпасть), шифруется AES-256-GCM и кладётся в базу; в журнал попадает только адрес.
   Ключ шифрования `WALLET_ENCRYPTION_KEY` генерируется автоматически при первом подключении и дописывается в `.env`.
   «Заменить» / «Отключить» — там же, отключение удаляет ключ из базы.
2. **Переключатель «Демо | Live»** — открывает подтверждение, где видно кошелёк, лимиты, состояние алертов,
   чекбокс **«Репетиция»** (dry-run) и поле **«Торговый капитал»** (база для расчёта размера позиции).
   После подтверждения движок сам перезапускается с новым режимом (2–3 секунды), демо-история остаётся отдельно.
3. **«Репетиция»** в карточке — включить/выключить dry-run одним нажатием, без правки файлов.
4. **«Сверить с цепочкой»** — сверка базы и ончейн-позиций.

API под этим: `POST /api/live/wallet`, `DELETE /api/live/wallet`, `POST /api/live/mode {mode, dryRun, capitalUsd}`.

## 5.3 Защита действий, которые трогают деньги

- Подключение/замена/отключение кошелька, переключение демо↔live, настройка алертов и сброс истории
  требуют **повторного ввода пароля администратора** (поле «Пароль» в блоке «Боевой режим»).
  Заголовок `x-admin-pass` проверяется на прокси (`timingSafeEqual`): одной украденной cookie недостаточно.
- Сессия живёт **7 дней** (было 30), настраивается `SESSION_DAYS`.
- **Жёсткий стоп по цене** (`HARD_STOP_PCT`, по умолчанию 8 %): если цена ушла ниже нижней границы
  диапазона на 8 % — выход немедленно (`EXIT_STOP`), не дожидаясь грейса. Защищает от дампов,
  которые диапазон не ограничивает (кейс HOTBOT: −29 % за 50 минут).
- Уходить в демо или включать репетицию при открытых live-позициях запрещено (409): иначе позиции
  остались бы в пуле без управления.

## 6. Порядок первого запуска (обязательный)

1. **Devnet** (≥ 48 часов): `SOLANA_RPC_URL` на devnet, те же лимиты, смотрим каждый шаг в explorer.
2. **Mainnet, малая сумма**: 0.3–0.5 SOL, `LIVE_MAX_POSITION_USD=25`, `MAX_POSITIONS=1`,
   1 неделя с ручным контролем. Критерий: капитал в базе совпадает с кошельком (±1%).
3. **Штатный режим**: поднимаем лимиты, оставляем сверку и алерты всегда включёнными.

Откат в любой момент:

```bash
sed -i 's/^LIVE_EXECUTION=.*/LIVE_EXECUTION=false/' /opt/meteora-terminal/.env
systemctl restart meteora-engine
```
Уже открытые позиции при этом остаются в пуле — их надо закрыть вручную в Meteora,
если не планируется вернуть live.
