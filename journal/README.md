# Журнал бота

Здесь живёт вся история решений. Формат рассчитан на то, чтобы **ИИ мог читать, парсить и находить ошибки**.

## Файлы

| Файл | Что внутри | Кто читает |
|---|---|---|
| `YYYY-MM-DD.md` | человекочитаемый поток решений и событий, в конце каждой строки — JSON-контекст | вы и ИИ (анализ) |
| `YYYY-MM-DD-summary.md` | итог дня: прогноз vs факт, ошибки модели, гипотезы | ИИ (улучшение стратегии) |
| `events.jsonl` | машинный поток, одна JSON-запись на строку (включая технический шум) | движок, скрипты аналитики |

Скачать журнал:

| Что нужно | Как |
|---|---|
| один день | интерфейс → **Кабинет → Журнал и диагностика → Скачать день**, или `GET /api/journal/download?date=YYYY-MM-DD` |
| **несколько дней одним файлом** | выберите «за N дн.» → **Скачать период**, или `GET /api/journal/download?days=7` |
| произвольный интервал | `GET /api/journal/download?from=2026-10-20&to=2026-10-28` |

Период склеивается в один markdown: шапка со списком дней и `## YYYY-MM-DD` перед каждым днём —
удобно отдать одним файлом ИИ и спросить «почему была просадка 27-го».

## Формат строк в `YYYY-MM-DD.md`

```
[HH:MM:SS] ТИП    подробности в одну строку `{"...": "json-контекст"}
```

Шапка дня (`CONFIG`) содержит полную конфигурацию: депозит, слоты, диапазон, фильтры,
`rangeDynamics` (как диапазон следит за ATR) и лимиты выхода. По ней ИИ понимает,
**в каких условиях** принималось каждое решение.

### Типы событий

**Торговля**

| Тип | Когда пишется | Что в JSON |
|---|---|---|
| `BOOT` | старт движка, восстановление состояния | mode, deposit, slots |
| `CONFIG` | параметры при старте | полный набор настроек |
| `SCAN` | проход скринера | пулы, отсев по причинам, лучший кандидат |
| `SCORE` / `REJECT` | оценка и отказ по фильтрам | score, ATR, причина отказа |
| `ENTER` | вход в позицию | capital, диапазон, ATR, прогноз |
| `FILL` / `MOVE` | перестановка сетки внутри диапазона | бины, цена |
| `CLAIM` | снятие комиссий | сумма, всего снято, кэш |
| `REBALANCE` | перестройка сетки после пробоя диапазона | диапазон было→стало, ATR было→стало, капитал, friction |
| `RANGE_ADJUST` | **правка диапазона из-за изменения ATR** (цена внутри) | `rangeFromPct`/`rangeToPct`, `atrFromPct`/`atrToPct`, drift, капитал, friction, `phase` |
| `RANGE_OUT` / `RANGE_BACK` | цена вышла за границу / вернулась (грейс 10 мин) | rel, rangePct, минуты |
| `ROTATE_WAIT` | позиция отработала срок и ждёт баланса для ротации | — |
| `EXIT_ROTATE` / `EXIT_RANGE_DOWN` | закрытие по ротации / пробою вниз | pnl, fees, slip |

**Контроль качества пула (новое)**

| Тип | Когда пишется | Что в JSON |
|---|---|---|
| `HEALTH` | периодический пересмотр пула (`healthCheckMinutes`) и пересмотр перед ребалансом | `verdict` (ok/soft/hard), `atrPct`, `atrAtEntry`, `atrDriftPct`, **`feeTvlPct`** (доходность пула, %/сут), **`bins`** (сколько бинов в сетке), `rangePct`, `rangePctTarget`, `rangeDriftPct`, `turnover24`, `tvl`, `inRangeShare`, `failed[]`, `warn[]`, `breachCount` |
| `EXIT_FILTERS` | **условия входа перестали выполняться** → выход вместо ребаланса | `failed[]` с фактическим значением и лимитом, `breachCount`, `confirmations`, `catastrophic` |

**Служебное**

`SNAP` (срез капитала каждые 5 мин: equity, drawdown, позиции, ATR/диапазон),
`SETTINGS` (дифф настроек было→стало, включая отклонённые параметры),
`STOP` (сработал лимит), `SUMMARY` (итоги 30 мин), `ERROR`, `WARN`, `HALT`, `LIVE`
(подтверждённые транзакции в боевом режиме), `MANUAL`, `DUPLICATE`.
Технический шум (`WS`, `FILL`, `SKIP`, `SCORE`) в `.md` не пишется — только в `events.jsonl`.

## Как читать прибыльность (новое)

Три числа объясняют почти любой результат:

1. **`feeTvlPct`** — комиссии пула за сутки на доллар TVL. Ниже 1.5 %/сут позиция не окупает обслуживание:
   `часов до окупаемости одного круга (≈0.65 %) = 0.65 / (feeTvlPct / 24)`.
   При 0.5 %/сут это 30 часов, при 4.6 %/сут — 3.4 часа.
2. **покрытие ATR** = `rangePct / atrPct`. Меньше 2 — позиция вылетает за 1–2 часа; при провале этого
   условия движок пишет `EXIT_FILTERS` («Диапазон покрывает ATR»).
3. **`bins`** — сколько бинов в сетке. Меньше 18 всего (9 на сторону) — это Spot-Concentrated,
   максимальный риск мгновенного выхода; такие пулы отсекаются ещё на входе.

В `ENTER` теперь пишется сумма и издержки входа (`C=$146 (вход $0.44)`), капитал в пуле (`netCapital`),
число бинов и `fee/TVL` пула.

## Как читать динамику диапазона

1. `ENTER` фиксирует `atrPct` и `rangePct` на входе — это база (`entryAtrPct`).
2. `HEALTH` показывает, куда движется волатильность: `atrDriftPct` — относительно входа,
   `rangeDriftPct` — насколько текущая сетка отличается от целевой (target = `rangeAtrMult × ATR`).
3. Если `|rangeDriftPct| ≥ rangeAdjustMinPct` и цена внутри диапазона → `RANGE_ADJUST`
   с фактическим пересчётом `rangeFromPct → rangeToPct` и `atrFromPct → atrToPct`.
4. Если `verdict = hard` (фильтр не проходит `filterBreachChecks` раз подряд или значение
   катастрофическое) → `EXIT_FILTERS` с точным списком провалов.

## Правило для ИИ при анализе

1. Читать `events.jsonl` (машинно) → строить агрегаты; `md` — для контекста и формулировок.
2. Для каждой закрытой позиции сравнивать `predictedDailyPct` (на входе) с фактическим `pnl_pct`.
   Систематическое расхождение > 30% → ошибка модели, а не «неудача рынка».
3. По `HEALTH` + `RANGE_ADJUST` проверять, не «пилит» ли бот диапазон: больше 3 правок за сутки
   на позицию при `lost=false` — повод увеличить `rangeAdjustCooldownMin` или `rangeAdjustMinPct`.
4. По `EXIT_FILTERS` смотреть, какой фильтр срабатывает чаще всего. Если это `turnover` —
   либо `minTurnover` слишком высокий для рынка, либо момент входа выбран на пике объёма.
5. Любой `ERROR` подряд ≥ 3 раз — искать причину в коде/лимитах API, а не «ретраить».
6. Гипотезы улучшений писать в `YYYY-MM-DD-summary.md` блоком `## Гипотезы`, а не менять логику молча.
